# GrantRadar — 補助金・公募情報の収集基盤

公開されている補助金・公募情報を毎日収集し、**前回との差分（新着・更新・掲載終了）を検知**して蓄積します。

このプロジェクトで示したいのは「スクレイピングができること」ではありません。
**取得してよいかを確認したうえで正しい手段を選び、失敗しても壊れない基盤を組めること**です。

毎日 09:00（JST）に GitHub Actions が実行し、結果を [`data/`](data/) に更新しています。
実際に動いている記録は [Actions のログ](../../actions/workflows/collect.yml)、
収集結果の推移は `data/` のコミット履歴で確認できます。

---

## 取得手段は「取れるか」ではなく「取ってよいか」で決めている

着手時に、候補サイトの `robots.txt` を実際に確認しました。

| サイト | `robots.txt` の応答 | 判断 |
|---|---|---|
| **jGrants**（補助金電子申請システム） | `User-agent: *` / `Disallow: /` / `Allow: /index.html` | ❌ **トップ以外のクロールが禁止**。画面からは取得しない |
| 調達ポータル | HTTP 401 | ❌ 認証が必要。対象外 |
| 中小企業庁 | HTTP 403 | ❌ 自動アクセスを拒否している |
| 国土交通省 | HTTP 404（`robots.txt` なし） | △ 明示的な許可も禁止もなし |

**官公庁のサイトだから自由に取得してよい、ということはありませんでした。**

jGrants は画面のクロールを禁止していますが、デジタル庁が
[公開API](https://developers.digital.go.jp/documents/jgrants/api/) を提供しています。
そこで **HTML を解析せず、公式API から取得しています。**

この判断はコードにも残しています（[`sources/jgrants.py`](src/grant_radar/sources/jgrants.py) の
モジュール docstring と `access_note`）。実行時にも毎回ログへ出力されます。

```
収集中: jgrants（official_api / サイトの robots.txt が Disallow: / のためスクレイピングは行わず、
デジタル庁が公開している公式APIを使用している）
```

### HTML を取得する場合は、必ず robots.txt を確認してから

将来 HTML の解析が必要な収集元を追加する場合に備えて、
**確認を省略できない経路**を用意しています（[`robots.py`](src/grant_radar/robots.py)）。

```python
fetcher = RobotsAwareFetcher(client)
body = fetcher.get(url)  # 禁止されていれば None を返し、理由を記録する
```

判断に迷う状況では、**取得しない側に倒しています。**

| 状況 | 判断 | 理由 |
|---|---|---|
| `robots.txt` が 404 | ✅ 取得する | 制限していないと解釈する（RFC 9309） |
| `robots.txt` が 401 / 403 | ❌ 取得しない | `robots.txt` すら見せないサイトは自動アクセスを歓迎していない |
| `robots.txt` が取得できない（通信断） | ❌ 取得しない | 許可されているとは言えない |
| **`robots.txt` が HTML で返る** | ❌ 取得しない | 404 の代わりに HTML を返すサイトが実在する。解析すると「禁止ルールなし」＝許可と誤読する |
| `Crawl-delay` の指定がある | ⏱ 従う | 自分の設定より長ければそちらに合わせる |

取得しなかった URL とその理由は記録されます。
**「落ちた」のか「禁止されていた」のかが区別できないと、収集漏れの原因を追えない**ためです。

## 機能

- jGrants 公式API からの収集（複数キーワードで検索し、重複を排除）
- **差分検知**（新着 / 更新 / 掲載終了）
- SQLite への蓄積（`first_seen_at` / `last_seen_at` を保持）
- 受付中の公募の抽出
- **CSV 出力**（Excel で文字化けしない BOM 付き UTF-8 / CRLF / 数式インジェクション対策）
- JSON 出力、人が読む Markdown 要約の生成
- GitHub Actions による定期実行と、結果の自動コミット

## 設計上の判断

実装で迷いやすい箇所について、何を選んだかと理由を残しています。

### 「前回あったのに今回無い」を、すぐ「終了した」と判断しない

差分検知でいちばん壊れやすい部分です。公募が実際に終了した場合と、
**API が落ちていただけ**の場合とで、データ上はまったく同じ状態になります。

取り違えると、募集中の公募を「終了した」と扱って見落とします。そこで、

- **収集が成功したときだけ**「掲載終了」を判定する
- レコードは削除せず `last_seen_at` を更新する

としています。消さずに残せば「いつまで見えていたか」を後から追えます。

### 1つの収集元が失敗しても、取れた分は捨てない

このAPIは `keyword` が必須で、全件を一度に取得できません。
そのため複数キーワードで検索して結果を統合しています。

一部のキーワードが失敗したとき、全体を失敗にすると**取得できた分まで失います**。
`CollectionResult` に「収集できたもの」と「失敗の記録」を並べて持たせ、
取れた分は保存しつつ、欠けていることを記録します。

### 上限額の `0` を、そのまま保存しない

API は上限額が未設定の公募に `0` を返します。これを保存すると
**「上限0円の公募」として集計され、金額での絞り込みが静かに壊れます。**
受け取った時点で `None` に寄せています。

### 再試行するステータスを限定する

`429` と `5xx` だけ再試行し、`404` や `403` は再試行しません。
何度投げても結果が変わらないものを繰り返し叩くのは、相手にとっては単なる連続アクセスです。
再試行には指数バックオフとジッタを入れています。

### レート制限はホスト単位で持つ

全体で1本にすると、無関係なホストへのアクセスまで待たされます。
ホストごとに最終アクセス時刻を持ち、独立して間隔を空けています。

### User-Agent に連絡先を含める

```
grant-radar/0.1.0 (+https://github.com/wutianheye051/grant-radar)
```

技術的な要件ではなくマナーの問題です。匿名のクローラは遮断されやすく、
遮断されなくても、迷惑をかけたときに相手が連絡する手段がなくなります。

### 外部APIのレスポンスを pydantic で受ける

外部APIはこちらの都合と関係なく変わります。
**壊れたデータを DB に入れてから気づくと、どこまで巻き戻せばよいのか分からなくなります。**
受け取った瞬間に検証しています。

### 定期実行では前回のデータベースを復元する

GitHub Actions は毎回まっさらな環境で動くため、そのままでは
**すべての公募が「新規」として報告されます。** `actions/cache` で SQLite を引き継いでいます。

## 使い方

前提: Python 3.12 以上

```bash
python -m venv .venv
.venv/bin/pip install -e ".[dev]"      # Windows: .venv\Scripts\pip
```

```bash
# 収集して差分を表示する
python -m grant_radar.cli collect

# あわせて data/ に JSON・CSV・要約を出力する
python -m grant_radar.cli collect --export

# 保存済みの受付中公募を一覧する
python -m grant_radar.cli list
```

終了コードは定期実行から使えるように意味を持たせています。

| コード | 意味 |
|---|---|
| `0` | 正常 |
| `1` | 一部の収集元で失敗した（取得できた分は保存済み） |
| `2` | 実行そのものに失敗した |

## テスト

```bash
pytest --cov=grant_radar --cov-report=term-missing
```

**38件 / カバレッジ 96%。** 外部APIには接続せず、`respx` で応答を模しています。

特に重点を置いたのは次の2つです。

- **`tests/test_robots.py`** — 「許可されていないのに許可と判断する」バグは、相手に迷惑をかける形で表面化します。404 / 401 / 403 / HTML応答 / 通信断 / `Crawl-delay` / キャッシュを網羅しています
- **`tests/test_store.py`** — **収集に失敗したときに「掲載終了」と判定しないこと**を明示的に検証しています

品質チェックは CI で実行しています（`ruff check` / `ruff format --check` / `mypy --strict` / `pytest`）。

## ディレクトリ構成

```
src/grant_radar/
  http.py            HTTPクライアント（タイムアウト・リトライ・レート制限）
  robots.py          robots.txt の確認。取得の可否と理由を返す
  models.py          収集した公募の型（pydantic）
  store.py           SQLite への保存と差分検知
  export.py          CSV / JSON / Markdown の出力
  cli.py             コマンドラインの入口
  sources/
    base.py          収集元の共通インターフェース
    jgrants.py       jGrants 公式API からの収集
tests/               38件
data/                収集結果（Actions が毎日更新）
.github/workflows/
  ci.yml             lint・型チェック・テスト
  collect.yml        毎日の収集と自動コミット
```

## 今後の拡張余地

実案件で最初に必要になる部分を挙げておきます。

- 条件（業種・地域・金額）に合う公募だけを通知する仕組み
- HTML を解析する収集元の追加（`robots.txt` で許可されている対象に限る）
- 収集失敗が続いた場合の通知
- 公募の詳細ページからの追加情報の取得（jGrants API の詳細エンドポイント）
